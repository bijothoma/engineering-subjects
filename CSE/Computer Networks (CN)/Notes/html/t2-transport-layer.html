Transport Layer

Unit 2 (weeks 6-8) · Kurose & Ross Ch. 3 (3.1-3.8) · also Peterson-Davie Ch. 5-6, Tanenbaum Ch. 6

1. Transport-layer services (K&R 3.1)

Definition. A transport protocol provides logical communication between application processes running on different hosts. The network layer provides logical communication between hosts (best-effort IP). Transport runs only in end systems; routers do not look at segments.
  • Sender: breaks application messages into segments, passes them to the network layer. Receiver: reassembles and delivers to the right socket.
  • Internet offers two: UDP (unreliable, unordered, connectionless) and TCP (reliable, in-order, flow control, congestion control, connection-oriented).
  • Services NOT available at transport layer because IP is best-effort: delay guarantees and bandwidth guarantees.

2. Multiplexing and demultiplexing (3.2)

Idea. Multiplexing: gather data from many sockets, add a header (source port, destination port) and hand it to IP. Demultiplexing: use header fields to deliver a segment to the correct socket. Ports are 16-bit; 0-1023 are well-known (80 HTTP, 53 DNS, 25 SMTP).
Segment header (common start):   | src port (16) | dst port (16) | ... other fields ... | application data |
UDP (connectionless demux)TCP (connection-oriented demux)
Socket identified by(dst IP, dst port)(src IP, src port, dst IP, dst port)
EffectDatagrams from different senders to the same dst port reach the SAME socketEach connection has its own socket; a web server may run one process with many connection sockets, all on port 80

Worked example. Server listens on port 80. Hosts A and B each open one connection (client ports 26145 and 7532); A opens a second one from port 26146. Server has three connection sockets, told apart only by the 4-tuple, though every segment has dst port 80.

Pitfall. Saying "TCP demultiplexes by port number" - port alone is not enough; the whole 4-tuple is used.

3. UDP (3.3)

"Bare-bones" transport: multiplex/demux plus optional error checking. Header is 8 bytes: source port, dest port, length (header + data), checksum (2 bytes each).

Why UDP? no handshake delay (DNS, QUIC), no connection state at server, small header, no congestion control throttling (good for real-time, but can harm others). Used by DNS, SNMP, streaming, VoIP, and QUIC. Reliability, if needed, is added in the application.

Internet checksum

sender:   treat segment (+ pseudo-header) as a sequence of 16-bit words
          sum = 0
          for each word w: sum = sum + w ; if carry out of bit 16: wrap around (add carry to LSB)
          checksum = ~sum            (1's complement)
receiver: add all words including checksum; result must be 1111111111111111, else error

Worked example (K&R). Words 0110011001100000, 0101010101010101, 1000111100001100.
first two: 1011101110110101; plus third: 1 0100101011000001 -> wrap carry: 0100101011000010 (sum).
Checksum = 1's complement = 1011010100111101. Receiver: sum + checksum = 1111111111111111, OK.

Pitfalls. The checksum cannot detect swapped 16-bit words or compensating errors (sum is commutative); it is weaker than a CRC. Detection is not correction: UDP just discards or passes the damaged data with a warning. Complexity: O(n) over the segment length.

4. Principles of reliable data transfer (3.4)

Goal: a reliable service abstraction over an unreliable channel that may corrupt, lose and (with long paths) reorder packets. We build it incrementally; communication is one-way data, two-way control.

ProtocolChannel assumptionMechanisms added

wait for ACK 0:  if corrupt or ack==1: do nothing
                 if timeout: udt_send(pkt0); restart_timer
                 if ACK 0 ok: stop_timer; go to "wait for call 1"
receiver: if pkt ok and seq==expected: deliver, send ACK(seq); else send ACK(last good seq)

Correctness idea. Sequence numbers distinguish new data from retransmissions; timer guarantees progress after loss; premature timeouts only cause harmless duplicates that the receiver discards.

Stop-and-wait performance. Utilisation U = (L/R) / (RTT + L/R).
Example: L = 8000 bits, R = 1 Gbps, RTT = 30 ms: D = 8 µs, U = 0.008 / 30.008 = 0.00027 (0.027%); throughput ~ 267 kbps on a 1 Gbps link.
Pipelining with window N: U = N x D / (RTT + D). N = 3 gives 0.00080; N needed for ~100% is about (RTT + D)/D = 3751.

Worked example (GBN, N = 4). Send 0,1,2,3; packet 1 lost. Receiver gets 0 (ACK 0), then discards 2 and 3 (re-sends ACK 0 twice). Timeout for 1: sender resends 1,2,3 (3 packets). SR would resend only 1 and receiver would have buffered 2, 3, ACKed individually.

Pitfalls. SR window larger than half the sequence space makes a retransmitted old packet look like new data (e.g. 3-bit space, window 5+). Window must also cover the bandwidth-delay product to keep the pipe full. Complexity: GBN simple receiver but wastes bandwidth on retransmissions (up to N per loss); SR needs buffers and per-packet timers.

5. TCP (3.5)

Properties. Point-to-point (one sender, one receiver), reliable in-order byte stream, pipelined (window set by flow + congestion control), full duplex, connection-oriented (three-way handshake), MSS limits the segment payload (typically 1460 bytes over Ethernet).

Segment structure

| src port 16 | dst port 16 |
| sequence number 32 |
| acknowledgement number 32 |
| hdr len 4 | unused | URG ACK PSH RST SYN FIN | receive window 16 |
| checksum 16 | urgent ptr 16 |
| options (MSS, window scale, SACK, timestamps) | data ... |
Header: 20 bytes without options.
  • Sequence number = byte-stream number of the first data byte in the segment. ACK number = next byte expected from the other side (cumulative). Out-of-order handling is left to the implementation (usually buffers).
  • Example: 500-byte segments with seq 1000, 1500, 2000. Receiver has bytes 1000-1999: ACK = 2000. Telnet echo: A sends seq=42, ack=79, 'C'; B replies seq=79, ack=43, 'C'; A ACKs seq=43, ack=80 (piggybacking).

RTT estimation and timeout

EstimatedRTT = (1-α)·EstimatedRTT + α·SampleRTT          α = 0.125
DevRTT       = (1-β)·DevRTT + β·|SampleRTT - EstimatedRTT|   β = 0.25   (uses OLD EstimatedRTT)
TimeoutInterval = EstimatedRTT + 4·DevRTT

Worked example. Est = 100, Dev = 10, sample 120: Dev = 0.75·10 + 0.25·20 = 12.5; Est = 0.875·100 + 0.125·120 = 102.5; Timeout = 102.5 + 50 = 152.5 ms. Next sample 80: Dev = 9.375 + 5.625 = 15; Est = 99.6875; Timeout = 99.6875 + 60 = 159.7 ms.

Initial timeout is 1 s; on timeout the interval is doubled (exponential backoff). Karn's algorithm: never sample RTT from retransmitted segments (ambiguous ACK). Only one segment at a time is timed.

Reliable data transfer in TCP

loop forever:
  data from app:   create segment (seq=NextSeqNum); start timer if not running; send; NextSeqNum += len
  timeout:         retransmit the not-yet-ACKed segment with SMALLEST seq (only that one); double timeout; restart timer
  ACK y received:  if y > SendBase: SendBase = y; if unACKed segments remain, restart timer
                   else (duplicate): count++; if count == 3: fast retransmit the segment starting at y

It is a hybrid of GBN (cumulative ACK, single timer) and SR (only the missing segment is resent, receiver buffers). Receiver ACK policy: in-order segment, previous ACKed: delay up to 500 ms for another; in-order with pending delayed ACK: send cumulative ACK immediately; out-of-order (gap): immediate duplicate ACK; segment that fills a gap: immediate ACK.

Fast retransmit. Segments 1,2,4,5,6 arrive (3 lost): 4,5,6 give three duplicate ACKs for 3's sequence number, so the sender resends segment 3 without waiting for the timer. Three (not one) avoids reacting to simple reordering.

Pitfalls. A premature timeout resends only one segment, not the window. ACK number is the NEXT byte, not the last received one. TCP does not "ack the ACK".

Flow control

Goal: the sender must not overflow the receiver's buffer. Receiver advertises rwnd = RcvBuffer - (LastByteRcvd - LastByteRead); sender keeps LastByteSent - LastByteAcked ≤ rwnd. Example: RcvBuffer 4096, LastByteRcvd 3000, LastByteRead 1800: rwnd = 4096 - 1200 = 2896. If rwnd = 0 the sender keeps sending 1-byte probe segments so it learns when space is free again. Window-limited throughput is at most window / RTT: 65535 B per 50 ms = 10.5 Mbps, hence the window-scale option for long fat networks.

Pitfall. Flow control (receiver protection) is not congestion control (network protection); the effective window is min(cwnd, rwnd).

Connection management

Open (3-way handshake):
 client                          server
  SYN, seq=x            --->     (allocate buffers)
  SYN-ACK, seq=y, ack=x+1 <---
  ACK, seq=x+1, ack=y+1 --->     (may carry data)
Close (4-way):  FIN  -> ACK ;  FIN  <- ACK ;  active closer waits in TIME_WAIT (2·MSL, e.g. 30-120 s)

Example: ISNs 400 and 900: third segment has seq=401, ack=901 (SYN and FIN each consume one sequence number). TIME_WAIT lets the final ACK be retransmitted and kills stray old segments. RST is sent if no matching socket exists (closed port). SYN flood: attacker leaves half-open connections; defence is SYN cookies (state encoded in the server ISN, no memory used until the final ACK). Simplified FSM states: CLOSED, LISTEN, SYN_SENT, SYN_RCVD, ESTABLISHED, FIN_WAIT_1/2, CLOSING, TIME_WAIT, CLOSE_WAIT, LAST_ACK.

6. Principles of congestion control (3.6)

Congestion = too many sources sending too fast for the network to handle: long delays (queues) and loss. Scenarios: (1) one router, infinite buffer: delay grows without bound as rate → capacity; (2) finite buffer + retransmissions: throughput below the offered load, unneeded duplicates; (3) multihop: when a packet is dropped downstream, the upstream capacity used for it is wasted, which can drive throughput towards zero (congestion collapse).

Approaches: end-to-end (TCP: infer from loss/delay) vs network-assisted (router feedback, ECN bits, ATM ABR).

7. TCP congestion control (3.7)

Idea. Sender limits LastByteSent - LastByteAcked ≤ min(cwnd, rwnd); rate ≈ cwnd / RTT. cwnd changes: ACKs mean the network is delivering, so increase; loss means congestion, so decrease. TCP is "self-clocking".
  • Slow start (cwnd = 1 MSS, doubles every RTT: +1 MSS per ACK) until cwnd reaches ssthresh, or loss.
  • Congestion avoidance (additive increase): cwnd += MSS·(MSS/cwnd) per ACK, about +1 MSS per RTT.
  • Loss (multiplicative decrease): ssthresh = cwnd/2.
    • Timeout: cwnd = 1 MSS, slow start (Tahoe and Reno).
    • 3 duplicate ACKs: Tahoe: cwnd = 1, slow start. Reno: fast recovery: cwnd = ssthresh + 3 MSS, +1 MSS per further dup ACK, deflate to ssthresh when new data is ACKed, then congestion avoidance.
on ACK of new data:   if cwnd < ssthresh: cwnd += MSS          (slow start)
                      else:               cwnd += MSS*MSS/cwnd  (congestion avoidance)
on timeout:           ssthresh = max(cwnd/2, 2 MSS); cwnd = 1 MSS
on 3 dup ACKs (Reno): ssthresh = cwnd/2; cwnd = ssthresh + 3 MSS; retransmit

Worked trace (units of MSS, per RTT; init ssthresh 16): cwnd = 1, 2, 4, 8, 16, 17, 18, 19. Timeout at 19: ssthresh = 9, restart 1, 2, 4, 8, 9, 10, ... With triple dup ACK at 20: ssthresh = 10, cwnd = 13 (Reno).

Throughput and fairness

AIMD sawtooth between W/2 and W: average throughput = (3/4)·W / RTT. Example: W = 40 segments, MSS 1000 B, RTT 100 ms: 0.75·40·8000/0.1 = 2.4 Mbps. With loss rate L: throughput ≈ 1.22·MSS / (RTT·√L). MSS 1460 B, RTT 100 ms, L = 10-4: 14.2 Mbps. To fill 10 Gbps at RTT 100 ms, MSS 1500 B: W ≈ 83,333 segments and L ≈ 2·10-10, which is unrealistic, hence new high-speed variants.

Fairness. K connections sharing a bottleneck of rate R each get about R/K under AIMD (the trajectory converges to the equal-share line since additive steps are equal and multiplicative cuts hurt the larger flow more). Fairness is per connection, so a host opening 9 parallel connections against a host with 1 gets 9R/10. UDP flows are not cwnd-limited and can squeeze TCP out.

ECN (explicit congestion notification): routers mark IP header bits (instead of dropping) and the receiver echoes via TCP ECE flag; the sender reduces cwnd as for loss.

Pitfalls. cwnd resets to 1 on timeout but NOT to 1 in Reno fast recovery. Slow start is exponential, not slow. ssthresh is half of cwnd at loss, not half of the old ssthresh. Delay-based schemes treat rising RTT, not loss, as congestion.

Quick revision

  • Transport = process-to-process; UDP demux by 2-tuple, TCP by 4-tuple.
  • UDP header 8 B; checksum = 1's complement of wrapped 16-bit sum (swapped words go undetected).
  • rdt: checksum → ACK/NAK → seq numbers → timers; stop-and-wait U = D/(RTT + D); pipelining multiplies by N.
  • GBN: cumulative ACK, receiver window 1, resend all; SR: per-packet ACK/timer, buffers; SR window ≤ half the seq space, GBN ≤ 2^k - 1.
  • TCP: byte-stream seq numbers; ACK = next byte expected; Timeout = EstRTT + 4·Dev; α = 1/8, β = 1/4; Karn's rule; fast retransmit after 3 dup ACKs.
  • Flow control: rwnd = RcvBuffer - (LastByteRcvd - LastByteRead); throughput ≤ window/RTT.
  • Handshake: SYN(x), SYN-ACK(y, x+1), ACK(x+1, y+1); TIME_WAIT 2 MSL; SYN cookies against SYN floods.
  • Congestion: slow start (exponential) → congestion avoidance (+1 MSS/RTT); timeout: ssthresh = cwnd/2, cwnd = 1; Reno 3 dupACKs: cwnd = ssthresh + 3.
  • Throughput = 0.75·W/RTT = 1.22·MSS/(RTT·√L); fairness per connection; ECN marks instead of drops.
  • CUBIC, BBR, DCTCP, SACK, QUIC (UDP-based, 0/1-RTT handshake, independent streams) are the "new" transports.
